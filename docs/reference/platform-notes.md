# Platform notes

Gotchas in the Windows and FFmpeg APIs Backsight uses: the things that compile fine and then fail at runtime. Read the relevant section before writing platform code, and **add to it** when you learn something the hard way. *(verify)* marks entries believed true but not yet confirmed on real hardware.

## Screenshot clipboard and publication

- JPEG XR screenshots use a separate WGC pool and staging texture in [RGBA16 float](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture). The [WIC JPEG XR codec](https://learn.microsoft.com/en-us/windows/win32/wic/-wic-codec-native-pixel-formats) accepts RGBA half-floats as scRGB without a color profile. Check the format `SetPixelFormat` returns before writing; WIC can substitute another. The picker and clipboard get an SDR rendition of the same frame.
- [SetClipboardData](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setclipboarddata) needs movable global memory and a real owner window: `OpenClipboard(None)` then `EmptyClipboard` gives a null owner and publishing fails. A hidden predefined `STATIC` window on the screenshot worker owns immediate `CF_DIB` data. Free the memory only on failure (Windows owns it after success). Allocate before emptying the clipboard. The final `GlobalUnlock` may report zero on success.
- `CF_DIB` is a `BITMAPINFOHEADER` plus DWORD-aligned rows, without the BMP file header. Positive height means bottom-up. Copy WGC rows using `RowPitch` and force opaque alpha.
- [MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw) with flags zero publishes a closed, flushed same-folder `.part` without replacing an existing file or needing hardlinks. Not a power-loss guarantee on every filesystem.
- Don't initialize and tear down WinRT around each screenshot: a second capture crashed in windows-core's cached factory after a per-call `RoUninitialize`. Match ReplaySession and let windows-core's activation fallback keep MTA in use.

## D3D11 device

- Create the device on the **encoder's adapter** (see [capture-pipeline.md](../architecture/capture-pipeline.md)), with `D3D11_CREATE_DEVICE_BGRA_SUPPORT` (WGC) and `D3D11_CREATE_DEVICE_VIDEO_SUPPORT` (`ID3D11VideoProcessor`).
- The capture thread, converter and FFmpeg's encoder thread share the device. Turn on `ID3D11Multithread::SetMultithreadProtected(TRUE)` and make FFmpeg use the same lock: set `AVD3D11VADeviceContext.lock`/`unlock` to callbacks that take it, or leave both unset so FFmpeg makes its own mutex. Never mix.
- **WARP has no video support.** `VIDEO_SUPPORT` on WARP fails with `DXGI_ERROR_UNSUPPORTED`; without the flag `ID3D11VideoDevice` is missing (`E_NOINTERFACE`). WARP (CI, PCs without a GPU driver) can't run the converter; tests that need it skip on vendor `0x1414`.
- `IDXGIAdapter::CheckInterfaceSupport(IDXGIDevice::IID)` returns the user-mode driver version as four 16-bit parts (WARP too). Adapter order changes with docking, so sort before using the list as a cache key.
- On `DXGI_ERROR_DEVICE_REMOVED` or `DEVICE_RESET` (driver updates, TDRs) rebuild everything: device, frame pool, converter, encoder.

## Windows.Graphics.Capture

- Wrap the D3D11 device for WinRT with `CreateDirect3D11DeviceFromDXGIDevice`, then cast to `IDirect3DDevice`. In `windows` 0.61 that `IDirect3DDevice` is not `Send`: keep the `ID3D11Device` and re-wrap it when calling `Recreate`.
- Create items with `IGraphicsCaptureItemInterop::CreateForMonitor` / `CreateForWindow` (desktop apps can't use the picker-only paths).
- Use `Direct3D11CaptureFramePool::CreateFreeThreaded`. The other pool needs a `DispatcherQueue` on the calling thread and silently never fires without one.
- **Release frames fast.** The pool has 2-3 buffers; holding a `Direct3D11CaptureFrame` stalls capture. Replay keeps at most one frame (a clone of the WinRT frame keeps its texture out of the pool), only until a newer frame replaces it or its pacer slot converts it. `Converter::convert_from` makes a video processor input view directly on WGC's texture, cached per pool texture; this works on NVIDIA drivers, so no BGRA copy is needed.
- A frame is checked out by `TryGetNextFrame` and back in when the `Direct3D11CaptureFrame` is released, from any thread (agile). `Recreate` with frames out discards them (Microsoft recommends draining first); a cloned texture stays alive through COM but is stale. The docs are silent on a frame outliving its pool's `Close`: release the held frame before dropping a window capture, and never while holding a lock the callback waits on.
- **Frames arrive only when content changes.** The pacer must repeat the last frame; never assume a steady callback rate.
- When `ContentSize` changes, call `Recreate` with the new size and rebuild the converter. **After a size change WGC sends a new frame only when content changes again**, and `deliver` drops the first frame at the new size (the pool still has the old one). A window that never repaints after a resize stays on its old picture; games repaint every frame, so this only matters for tests (make the test window repaint, e.g. `SetWindowTextW` in a loop).
- **Window items** (`CreateForWindow`, Windows 10 1903+; `windows` 0.61: `unsafe fn CreateForWindow<T: Interface>(&self, HWND) -> Result<T>`) capture the **extended frame bounds** (`DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`) in physical pixels, not `GetWindowRect`, which includes invisible resize borders. On Windows 11 24H2 (build 26100) and later: a maximized 1920x1080 window gives 1920x1032 against `GetWindowRect` 1936x1048 (`tests/screenshot.rs`); a 640x480 `WS_OVERLAPPEDWINDOW` (per-monitor-v2, 100% scaling) gives 626x473 (`tests/window_capture.rs`). Microsoft's docs say nothing about what the size covers or about DPI.
- `GetWindowRect`/`DwmGetWindowAttribute` rects are physical pixels only in a per-monitor-DPI-aware process. WGC's sizes don't depend on our awareness, so the engine never computes window rects itself.
- `GetForegroundWindow` returns `Progman`/`WorkerW` when the desktop has focus and `Shell_TrayWnd`/`Shell_SecondaryTrayWnd` for taskbars. Window screenshots fall back to the monitor for those, for minimized (`IsIconic`) or invisible windows, and for our own windows. A minimized window delivers no new frames (at most one during the animation; no error, `Closed` doesn't fire), so a window shot would only time out and window recording repeats its last picture.
- `FrameArrived` on a free-threaded pool may not be serialized (docs don't say), so the handler keeps all state behind one lock. `GraphicsCaptureItem.Closed` is documented only as "the target has been closed"; it fires within 1.5 s of `DestroyWindow` on a captured window (recent Windows 11 builds). That it fires on monitor unplug is *(verify)*; the app also restarts replay when the captured monitor leaves `EnumDisplayMonitors` (checked every 5 s, twice in a row).
- **Window capture follows the game's window** (`session::follow_window`, ADR 0012): output size stays fixed and other shapes are fitted with black bars by the video processor (`VideoProcessorSetStreamDestRect`, `VideoProcessorSetOutputBackgroundColor`). For an NV12 output give the background **in YCbCr** (`ycbcr = TRUE`, studio black Y 16/255, Cb = Cr = 0.5): RGBA black came out as Y = 0, below video black (`convert.rs` test `another_shape_gets_black_bars`). The [docs](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11videocontext-videoprocessorsetoutputbackgroundcolor) say nothing about range or conversion, so this is driver behaviour. Verified on NVIDIA and Intel; AMD is *(verify)*.
- **Video processor size limits:** [`D3D11_VIDEO_PROCESSOR_CAPS`](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ns-d3d11-d3d11_video_processor_caps) and [`D3D11_VIDEO_PROCESSOR_CONTENT_DESC`](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ns-d3d11-d3d11_video_processor_content_desc) state no maximum size: any ceiling is the driver's, and `CreateVideoProcessorEnumerator` just errors. A converter rebuild for a new window size can fail; window mode treats that like a lost window and retries after 2 s. The docs don't say whether a Blt input may differ in size from the content description, so Backsight rebuilds the converter on every size change, once the size has held 150 ms (`target::SizeSettle`; dragging an edge changes size nearly every frame). A still window resized once may send no frame after that, so the video thread then uses the last frame it skipped.
- **Naming a monitor so it survives restarts:** the GDI name from `GetMonitorInfoW`/`MONITORINFOEXW` (`\\.\DISPLAY1`) is renumbered when plug order changes. `EnumDisplayDevicesW(szDevice, 0, &mut DISPLAY_DEVICEW, EDD_GET_DEVICE_INTERFACE_NAME)` gives the interface path in `DeviceID` (`\\?\DISPLAY#<EDID id>#<instance>#{e6f07b5f-…}`), stable across reboots and plug order but tied to the port. Backsight saves that (`wgc::monitors`) and falls back to the primary monitor when it's gone.
- `IsBorderRequired = false` and `IsCursorCaptureEnabled` exist only on newer builds: check with `ApiInformation::IsPropertyPresent`. Unpackaged, `SetIsBorderRequired(false)` works without `GraphicsCaptureAccess::RequestAccessAsync` (Windows 11 24H2 and later).
- `SystemRelativeTime` is QPC time in **100 ns units**, not raw ticks. Run the pacer at 10 MHz and convert `QueryPerformanceCounter` to match. QPC **keeps counting through sleep**, standby, hibernate and connected standby, so after waking frame times jump by the time slept; the replay buffer uses that to notice a sleep.
- `MinUpdateInterval` exists on Windows 11 24H2+ only; otherwise throttle in the pacer. It is a minimum gap and the real gap adds the wait for the game's next frame, so a cap near `1/fps` delivers fewer frames than `fps` (15 ms gave ~51 frames/s on a ~93 fps game). Replay uses half the frame interval. It can't help a game drawing fewer pictures than the recording rate; it only saves work when the game outruns the recording.
- **WGC itself costs a GPU-bound game FPS:** a monitor capture alone (no conversion or encoding) cost ~2.3% at 1440p. That is the floor for any WGC recorder; conversion added ~1.2 points and NVENC 2-3 more.
- **The pool textures' bind flags are undocumented.** OBS's `winrt-capture.cpp` and robmikh's Win32CaptureSample both `CopyResource` into their own texture first. The SDR video processor takes an input view directly on NVIDIA. The HDR converter (`hdr.rs::view_of`) reads `GetDesc().BindFlags`, makes a shader view when `D3D11_BIND_SHADER_RESOURCE` is set and the size matches, else copies the frame (30 MB at 1440p FP16) and logs the flags once *(verify which path an NVIDIA card takes)*.
- **Capturing a monitor wired to another graphics card than the capture device's** (laptop panel on Intel, device on NVIDIA) works, unlike Desktop Duplication, but Microsoft documents neither how the frame crosses nor its cost. DXGI lists a monitor under the card it is wired to (third-party evidence only). Replay logs that card next to the encoder's (`replay path: …`); measure with `scripts/replay-gpu-cost.ps1` (GPU use by card, engine type and process). The capture copies run in `dwm.exe`, not Backsight.
- **Window mode's take-over rule:** a windowed program takes over only when the captured program started it, or a listed launcher started it after the capture began (launchers are never captured). The parent PID comes from a `CreateToolhelp32Snapshot` entry (`th32ParentProcessID`), which Windows never updates when the parent exits, so the PID can be reused. `Program::launched_by` therefore also requires the child's creation time (`GetProcessTimes`, works with a `PROCESS_QUERY_LIMITED_INFORMATION` handle) to be no earlier than the parent's. A launcher that starts the game through a helper isn't matched; list the helper in `content/game-launchers.json`. The snapshot runs only when the game watcher decides a take-over, never before a screenshot. A program started by something else (a chat opened mid-game) never takes over unless it covers its monitor. A browser (`content/browsers.json`) never takes over at all: a game started with no browser running is the parent of the browser it opens, so the parent check alone would let it in.
- **Exclusive full screen in window mode:** Microsoft's `CreateForWindow` page says nothing about it. Third-party reports agree window capture can't see a game in true exclusive full screen (Discord's screen share says so; the composition pipeline WGC reads is skipped), and OBS issue #14021 reports monitor capture (WGC and Desktop Duplication) freezing on exclusive full screen on Windows 11 24H2 and later. So falling back to monitor capture isn't reliable either; Backsight tells the user instead. A game in front draws all the time, so when the captured window sends no frame for `target::EXCLUSIVE_QUIET` (2 s) while it is the foreground window and `SHQueryUserNotificationState` says `QUNS_RUNNING_D3D_FULL_SCREEN`, Home shows `target::WINDOW_EXCLUSIVE` (borderless or windowed works). A game whose exclusive mode Windows turns into a composed one (fullscreen optimizations) keeps sending frames, so the line never shows for it. *(Verify on a real exclusive-full-screen game: whether WGC sends black frames rather than none, which would hide the line.)*
- The process must be **per-monitor DPI aware (v2)**, or monitor sizes and the region picker will be wrong. Tauri's manifest does **not** declare it; tao calls `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` (falling back to v1, then `SetProcessDpiAwareness`) in `EventLoop::new` on the main thread (`dpi_aware` defaults to true), inside `Builder::build`, before `setup` and every engine thread. `cargo test` processes are DPI-unaware unless a test sets it.

## Region picker

- **Coordinates.** A thread without its own `SetThreadDpiAwarenessContext` uses the process's awareness ([docs](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setthreaddpiawarenesscontext)), so `GetCursorPos`, `MonitorFromPoint` and `GetMonitorInfoW` give physical virtual-screen pixels on any thread. Monitors left of or above the primary have **negative** coordinates ([The Virtual Screen](https://learn.microsoft.com/en-us/windows/win32/gdi/the-virtual-screen)). `MonitorFromPoint(..., MONITOR_DEFAULTTONEAREST)` always returns a monitor, even after a failed `GetCursorPos` (point 0,0).
- **WebView CSS pixels.** WebView2 lays out at physical ÷ `RasterizationScale`, which is the monitor scale *combined with the Windows text size setting* ([ICoreWebView2Controller3](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2controller3)), so the monitor scale alone can be wrong. The picker never converts with a scale factor: it stretches the frozen image over its whole view and sends the drag with `innerWidth`/`innerHeight`; `screenshot::area` scales by image ÷ view. Coordinates are relative to the picker's own top-left, so negative monitor origins matter only for placing the window.
- **Placing the window.** tao's `set_outer_position`/`set_inner_size` take physical values and post `SetWindowPos` with `SWP_ASYNCWINDOWPOS`. An undecorated window *with a shadow* gets a size offset, so the picker uses `shadow(false)`. Moving onto a monitor with another scale triggers tao's `WM_DPICHANGED` handler, which resizes and may move the window, so the picker is placed, sized, then placed again while hidden *(verify on a mixed-DPI setup)*.
- **Focus.** tao's `set_focus` tries `SetForegroundWindow` and, if the foreground lock refuses, sends a synthetic left Alt down/up with `SendInput` and retries. Our Raw Input listener sees that Alt; harmless unless a hotkey is Alt alone. wry moves keyboard focus into WebView2 on `WM_SETFOCUS`, so Esc reaches the page. Without focus, right-click still cancels.
- **Passing the picture.** A command returning `tauri::ipc::Response::new(Vec<u8>)` is sent raw as `application/octet-stream` and `invoke` resolves with an `ArrayBuffer`. The picker gets an uncompressed BMP (clipboard DIB plus a 14-byte file header) shown from a `blob:` URL (`img-src blob:` in the CSP): no encode, temp file or asset scope.
- **Permissions.** App commands from `generate_handler!` are not ACL-checked while `build.rs` declares no app manifest, so the picker needs no capability and gets no plugin access.
- **Page.** The picker loads `index.html?picker`; Tauri's protocol ignores the query when finding the file, and `main.ts` mounts `Picker.svelte` for it.
- A topmost window over a game in true exclusive fullscreen may make the game minimize; undocumented *(verify)*.

## NVENC through FFmpeg

- **Some NVENC features run on CUDA, shared with the game.** The NVENC Programming Guide (SDK 13.0, 6.4) lists two-pass rate control, look-ahead, all AQ modes, weighted prediction, RGB input and temporal filtering, with no numbers. In a GPU-bound game at 1080p60 H.264, turning off multipass, look-ahead and spatial AQ saved ~0.8-1.6 points of game FPS. B-frames are documented as having no performance impact.
- **Zero-copy path:** create an `AVHWDeviceContext` of type `AV_HWDEVICE_TYPE_D3D11VA` around **our** `ID3D11Device` (set `AVD3D11VADeviceContext.device`, then `av_hwdevice_ctx_init`). Build an `AVHWFramesContext` with `format = AV_PIX_FMT_D3D11`, `sw_format = NV12` (`P010` for 10-bit). Get frames with `av_hwframe_get_buffer` (`data[0]` = texture, `data[1]` = array index) and `CopySubresourceRegion` the converted texture into it. Set `initial_pool_size = 0`: a preallocated pool is one texture array, and the NVIDIA driver rejects NV12 arrays of more than **2 slices** with `E_INVALIDARG` unless they have `D3D11_BIND_DECODER`. With 0, FFmpeg allocates standalone textures on demand. Covered by `crates/backsight-engine/tests/capture_to_clip.rs`.
- **Capability differences:** AV1 needs RTX 40 (Ada)+. HEVC B-frames need Turing (RTX 20)+. 10-bit HEVC needs `P010` input and `profile=main10`. The probe must try the exact configuration (codec, bit depth, B-frames, resolution), not just "does `hevc_nvenc` open".
- **`hevc_nvenc` failing with "Generic error in an external library" on Pascal (GTX 10xx) is almost certainly `bf` > 0** (suspected on Pascal (GTX 10-series) GPUs; unconfirmed on real Pascal hardware). FFmpeg 8.1 `nvenc.c` never clamps B-frames to `NV_ENC_CAPS_NUM_MAX_BFRAMES`: `nvenc_check_capabilities` logs a WARNING ("Max B-frames 2 exceed 0") and returns `ENOSYS`, `nvenc_check_device` tears the session down, and `nvenc_setup_device` logs "No capable devices found" and returns `AVERROR_EXTERNAL`. So EXTERNAL from `avcodec_open2` on NVENC means "no GPU passed the capability checks" (B-frames, 10-bit, lossless, look-ahead, resolution, ...); the real reason is only in the WARNING line, which `errors_only_logging` hides. `nvEncInitializeEncoder` failures go through `nvenc_map_error` instead (`INVALID_PARAM` → `EINVAL`, `UNSUPPORTED_PARAM` → `ENOSYS`, else `AVERROR_UNKNOWN`), never EXTERNAL. Fix: the probe retries NVENC with `bf=0`, remembers `max_bframes = 0`, and opening a session forces `bf=0` for it; WARNING lines from probe opens go into the problem detail.
- **Opening NVENC is slow the first time in a process:** about 6-10 s (hybrid laptops wake the NVIDIA card first; longer from a slow drive), for whichever encoder a fresh process opens first (Quick Sync H.264 8.7 s, then HEVC 0.7 s). The per-encoder limit is 30 s; 10 s wrongly marked working NVIDIA encoders as stuck. When Instant Replay is off, `session::warm_up` opens and closes the chosen encoder once after startup so the first recording opens in well under a second *(verify: compare the log's "encoder warmed up" time with "video encoder after" in the next "replay starting" line, with a game running and the card asleep; if it stays at seconds, the cost is the card waking up and warming doesn't help)*.
- **Test processes die with Backsight.** `ProbeRun::drop` only kills the encoder-test child if the checking thread finishes, so each child joins one process-wide job object (`engine/src/job.rs`: `CreateJobObjectW`, `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` via `SetInformationJobObject`, `AssignProcessToJobObject`). The handle is never closed; Windows closes it when Backsight exits or is killed. A child can't join if Backsight runs inside a job that forbids nesting (rare; nested jobs work since Windows 8): that only costs a stray process.
- **Driver too old:** FFmpeg's NVENC needs a minimum driver matching its `nv-codec-headers`. The error mentions the required NVENC API version; map it to "Update your NVIDIA driver to use NVENC".
- **Concurrent sessions are limited on GeForce cards** (the cap has changed over time). The probe must close every test session; Backsight uses one encoder for both replay and recording.
- **FFmpeg 8.1's `nvenc.c` never calls `AVD3D11VADeviceContext.lock`/`unlock`.** It runs `nvEncEncodePicture` and `nvEncLockBitstream` synchronously on the thread calling `avcodec_send_frame`/`receive_packet` (`enableEncodeAsync = 0`), and NVIDIA's guide says `NvEncLockBitstream` "can internally use the application's DirectX device". So the caller holds `ID3D11Multithread::Enter` around send and receive (`Gpu::lock`).
- On some PCs `send` sometimes blocks 8-50 ms per frame at 1080p and 1440p alike, whatever the preset, multipass or look-ahead, while other runs hold 60 fps. It looks environmental (GPU power state, hybrid-laptop cross-adapter copy) *(investigate with PresentMon)*.
- Option values: `rc-lookahead` is a frame count, not a bool (the catalog toggle maps to a number in the family mapping). `multipass` takes `disabled`, `qres` or `fullres`. "Constant quality" is `rc=vbr` with `cq=N` and `b=0`, not `constqp`. Set `g` (GOP size in frames) explicitly: Instant Replay cut precision depends on it.
- **Forcing a keyframe** (recording resume): set the input `AVFrame.pict_type = AV_PICTURE_TYPE_I` (back to `NONE` for later frames). FFmpeg 8.0 `nvenc.c` turns that into `NV_ENC_PIC_FLAG_FORCEINTRA`, a plain I-frame, unless the private option `forced-idr` is 1 (default 0), and only `NV_ENC_PIC_TYPE_IDR` output gets `AV_PKT_FLAG_KEY`. Without `forced-idr=1` the forced frame is neither flagged nor safe to start a file on. libx264 maps it to `X264_TYPE_KEYFRAME` (an IDR with its default closed GOP) and flags the packet from `b_keyframe`. AMF and Quick Sync name the option `forced_idr` (default 0): AMF otherwise makes an unflagged plain I frame, so set it to 1; Quick Sync also makes an IDR when the frame carries `AV_FRAME_FLAG_KEY`. `VideoSession` sets whichever exists with `av_opt_set` before opening (not in the dictionary, which fails on unknown options). The forced frame comes out after the encoder's usual delay: x264 at 60 fps returned it 17 frames after it was sent (`tests/recording_cuts.rs`); NVENC (2 B-frames, no look-ahead) returned its first packet after the 11th frame, then one per frame, so anything sending frames sparsely waits ~10 frames. Recording accepts the first keyframe whose **pts** is no earlier than 100 ms before the resume press (the requested frame may already be captured), whenever it arrives; an encoder that ignores the request resumes at its next regular keyframe.
- With B-frames a packet decoded before a cut can be shown after it (I0 P3 B1 B2: P3 decodes before B1). Ending a file or pause anywhere in decode order is decodable, but end it just before a packet shown after every earlier one (an I or P frame), or a kept P-frame would display after the first frame following the cut.
- NVENC and Quick Sync also accept plain system-memory NV12 frames (FFmpeg uploads them). The encoder probe uses that and needs no D3D11 device; capture still uses D3D11 frames for zero copy.
- `av1_nvenc` has no `profile` option (FFmpeg 8.1); the catalog omits it with `"omit": true`.

## Option mapping per family (FFmpeg 8.1, checked with `ffmpeg -h encoder=<name>`)

- Only NVENC and AMF have an `rc` option. QSV, libx264/libx265, SVT-AV1 and libaom infer rate control: `global_quality` or `crf` for quality, `b` for VBR, `b` = `maxrate` = `bufsize` for CBR. libaom constant quality needs `crf` plus `b=0`.
- AMF `rc` names: `cqp`, `cbr`, `vbr_peak`, `vbr_latency`, `qvbr`, `hqvbr`, `hqcbr`. Constant quality is `qvbr` + `qvbr_quality_level`.
- x265 has no `film` tune, and with `tune=zerolatency` it refuses B-frames ("Lookahead depth must be greater than the max consecutive bframe count").
- String options (x264/x265 `preset`, `tune`, `profile`) pass `av_opt_set` with any value and fail only in `avcodec_open2`. Test them by opening the encoder.
- **rsmpeg 0.18 `AVCodecContext::open(Some(dict))` double-frees the dictionary when the open fails** (avcodec_open2 already replaced it) and crashes. Call `avcodec_open2` directly with a raw dictionary (`backsight-encode/src/ffmpeg.rs`).

## Muxing clips (FFmpeg 8.1)

- **Fragmented MP4/MOV with `empty_moov` starts every track's decode time at zero** (no edit list), pulling together audio and video that start at different times. Add `delay_moov`: the moov is written with the first fragment, edit lists keep each track's start, and the file is still crash-safe after that fragment. `tests/save_clip.rs` checks fragmented MP4, MOV, plain MP4 and MKV keep A/V within 1 ms.
- With B-frames a keyframe's decode time is before its display time. Start a clip's audio at the keyframe's **decode** time, the origin every container measures from.
- Clips start mid-stream, after the AAC encoder's 1024 priming samples, so set `codecpar.initial_padding = 0` when muxing; Matroska otherwise shifts audio one frame (21 ms) late.
- **What a crash leaves behind** (`backsight-encode/tests/crash_kill.rs`, `TerminateProcess`): crash-safe MP4 opens and plays every fragment before the last, which may be cut off; the file keeps its `.part` name. AVIO writes in 32 KB blocks and the mov muxer doesn't flush per fragment, so the newest ≤ 32 KB are lost too. With `delay_moov` nothing reaches disk before the first fragment (and its first 32 KB block): a kill inside the first GOP leaves an empty file. Set the `flush_packets` format option if low-bitrate recordings need less loss. Recordings are written as `<name>.recording.part` so `recovery` can find them; a killed crash-safe MP4 or MKV opens in FFmpeg up to the cut, and stream copy makes a normal file (`backsight-engine/tests/recovery.rs`).
- **A refused packet vs a failing drive.** `av_interleaved_write_frame` refuses a packet whose DTS doesn't increase (equal counts for MP4/MOV; Matroska has `AVFMT_TS_NONSTRICT` and takes equal ones) with `EINVAL` before writing any of it, so the copy can skip it; `pb->error` stays 0 (`tests/remux.rs`). A failed drive write sets `pb->error` (first error kept), and `write_packet`, `av_write_trailer` and `avio_close` then return it; `remux::copy` uses that to mark drive errors `CANT_WRITE` *(verify: read from FFmpeg's aviobuf.c/mux.c; no test fills a drive mid-copy)*.
- To tell whether another process is still writing a file, open it with `share_mode(0)`: Windows refuses with `ERROR_SHARING_VIOLATION` (32) while any other handle, including FFmpeg's, is open.

## Chapters (recording markers, FFmpeg 8.x)

Sources: `libavformat/movenc.c` (`mov_init`, `mov_write_header`, `mov_write_trailer`, `mov_create_chapter_track`, `mov_write_udta_tag`), `matroskaenc.c` (`mkv_write_chapters`, `mkv_write_trailer`), the `nb_chapters` doc in `avformat.h`; checked with `ffprobe -show_chapters` in `backsight-encode/tests/chapters.rs`.

- There is no public "add chapter" call (`avpriv_new_chapter` is private). `av_mallocz` an `AVChapter`, set `id`, `time_base`, `start`, `end` and a `title` in `metadata`, append with `av_dynarray_add_nofree(&s->chapters, &s->nb_chapters, c)`; `avformat_free_context` frees it (`mux::push_chapter`).
- **MKV:** chapters added after the header are written once, in `mkv_write_trailer`, if there were none at `write_header`. Start must be ≥ 0 and end ≥ start or the whole trailer fails; zero or duplicate ids are renumbered.
- **MP4/MOV, not fragmented:** the moov is written in the trailer, so late chapters get a Nero `chpl` atom (up to 255, start times only, unless `movflags=disable_chpl`) and a QuickTime chapter text track (created only if `nb_chapters` was 0 at `write_header`).
- **Fragmented MP4/MOV (`frag_keyframe+empty_moov+delay_moov`):** the moov goes out with the first fragment and is never rewritten, and the trailer's late-chapter code is skipped for fragments, so chapters added after the first fragment are **lost**. Chapters known before the header get a chapter track whose first sample starts at zero (no edit list). So a crash-safe recording with markers is copied once more at stop, as plain MP4/MOV with chapters set before the header (`Muxer::finish`); without markers it stays fragmented and isn't copied.
- **The chapter track always starts at zero**, fragmented or not: write a chapter at 0 ("Start") before the first marker, or the first marker reads back at 0 s. Backsight always does, in every container.
- FFmpeg's mov demuxer reads both `chpl` and the chapter track; with both present `ffprobe` showed each chapter once.
- MPEG-TS and FLV can't hold chapters (`mux::holds_chapters`). WebM can; not tested (needs AV1).
- An interrupted recording's markers are lost: they are written only when the file is finished.

## WASAPI

- Initialize COM as **MTA** on each audio thread.
- **Loopback delivers nothing while nothing plays.** Detect gaps from QPC timestamps and insert silence, or audio runs ahead of video. Event-driven loopback needs `AUDCLNT_STREAMFLAGS_LOOPBACK | EVENTCALLBACK` (Windows 10 1703+) and its event doesn't fire while nothing plays, so wait with a timeout (20 ms) and fill silence on each wake.
- Respect buffer flags: `AUDCLNT_BUFFERFLAGS_SILENT` (treat as zeros) and `DATA_DISCONTINUITY` (a glitch: log and resync). The first loopback packet after `Start` normally carries `DATA_DISCONTINUITY`; once per stream start is not a glitch.
- `GetBuffer`'s `pu64QPCPosition` is already in **100 ns units**, the same clock as WGC's `SystemRelativeTime`. Ignore it when the packet has `AUDCLNT_BUFFERFLAGS_TIMESTAMP_ERROR`.
- `AUTOCONVERTPCM | SRC_DEFAULT_QUALITY` works with loopback and microphones: ask for 48 kHz float stereo and Windows converts from the device's mix format, so no resampler is needed ("a channel matrixer and a sample rate converter as necessary", [stream flags](https://learn.microsoft.com/en-us/windows/win32/coreaudio/audclnt-streamflags-xxx-constants); no rate or channel limits documented). Checked (Windows 11 24H2 and later, `cargo test -p backsight-engine -- --ignored`) on 44.1 kHz render endpoints and 48 kHz stereo microphones; loopback delivered 47 988 frames/s (48 kHz plus normal drift, absorbed by the timeline). Windows also upmixes a mono mic. *Not yet checked: a 96 kHz device and a 5.1/7.1 device; run `every_endpoint_converts_to_48k_stereo` and `loopback_delivers_48k_whatever_the_device_rate` on one.*
- **Process loopback** (`ActivateAudioInterfaceAsync` with `VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK`) is asynchronous: wait for the completion handler. `GetMixFormat` isn't supported on that client, so pass an explicit format (48 kHz, float or 16-bit, stereo).
  - **Minimum build:** [AUDIOCLIENT_ACTIVATION_PARAMS](https://learn.microsoft.com/en-us/windows/win32/api/audioclientactivationparams/ns-audioclientactivationparams-audioclient_activation_params) and the sample's README say Windows 10 build 20348; the [ActivateAudioInterfaceAsync](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nf-mmdeviceapi-activateaudiointerfaceasync) page says 20438. OBS ships it with no build check and it is widely used on Windows 10 2004+ (19041), so Backsight refuses below 19041 and otherwise just tries *(verify on a Windows 10 PC)*. `GetVersionEx` reports Windows 8 to a process without a manifest (`cargo test`), so read `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\CurrentBuildNumber` (feature `Win32_System_Registry`).
  - **Threading:** desktop apps may call it from an MTA worker; only activations that can show a consent prompt (capture devices) need the UI thread, and process loopback shows none. Windows calls `ActivateCompleted` on an MTA worker thread. The handler must be agile; windows-rs `#[implement]` objects already answer `IAgileObject` and the free-threaded marshaler, but the macro expands to `::windows_core` paths, so the crate needs `windows-core` as a direct dependency.
  - **Activation params:** a `PROPVARIANT` with `vt = VT_BLOB` pointing at an `AUDIOCLIENT_ACTIVATION_PARAMS` (`PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE`). Never `PropVariantClear` it: the blob is our memory. In windows 0.61 `PROPVARIANT` **does** implement `Drop` (as `PropVariantClear`) once `Win32_System_Variant` is on, so wrap the hand-built one in `ManuallyDrop`. Read the result with `GetActivateResult` (an `HRESULT` plus the `IUnknown`, cast to `IAudioClient`) after the handler fires.
  - Initialize with `LOOPBACK | EVENTCALLBACK` (+ `AUTOCONVERTPCM`). A target that plays nothing (or has exited) gives silence, not an error, so the caller must watch the process.
- **Microphone** (`GetDefaultAudioEndpoint(eCapture, eConsole)` or `GetDevice(id)`) in shared mode. Errors from `IAudioClient::Initialize`: Settings > Privacy & security > Microphone blocking desktop apps gives `E_ACCESSDENIED` (0x80070005); no capture device or an unknown id gives `HRESULT_FROM_WIN32(ERROR_NOT_FOUND)` (0x80070490); another app holding it in exclusive mode gives `AUDCLNT_E_DEVICE_IN_USE`.
- Feature flags: `CreateEventW` needs the `windows` crate's `Win32_Security`; `IMMDevice::Activate` needs `Win32_System_Com_StructuredStorage` plus `Win32_System_Variant`.
- **Listing endpoints:** `EnumAudioEndpoints(eCapture, DEVICE_STATE_ACTIVE)`, then per item `GetId` (a `PWSTR` to copy, then `CoTaskMemFree`) and `OpenPropertyStore(STGM_READ)?.GetValue(&PKEY_Device_FriendlyName)`. Use `Win32::Devices::FunctionDiscovery::PKEY_Device_FriendlyName` (a `PROPERTYKEY`; `DEVPKEY_Device_FriendlyName` is a different type); `GetValue` needs `Win32_UI_Shell_PropertiesSystem`. The returned `PROPVARIANT` frees itself and `to_string()` gives the name. Ids are opaque: store and compare as given.
- **Device notifications (`IMMNotificationClient`)** ([interface](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nn-mmdeviceapi-immnotificationclient), [device events](https://learn.microsoft.com/en-us/windows/win32/coreaudio/device-events)):
  - Callbacks come on an unnamed system thread, so the object must be `Send + Sync`. They must not block or wait on a lock, must not call `Register`/`UnregisterEndpointNotificationCallback`, and must not release the last reference to an MMDevice object. Backsight only sets an atomic flag; the audio thread reopens.
  - [`UnregisterEndpointNotificationCallback`](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nf-mmdeviceapi-immdeviceenumerator-unregisterendpointnotificationcallback): the enumerator takes no reference of its own, so keep the client alive until Unregister returns. Backsight registers and unregisters on the capture thread, before `CoUninitialize`. Microsoft doesn't say Unregister waits for a callback already running, so Backsight leaks one reference to be safe.
  - [`OnDefaultDeviceChanged`](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nf-mmdeviceapi-immnotificationclient-ondefaultdevicechanged) fires once **per role** (`eConsole`, `eMultimedia`, `eCommunications`), so react only to the role you opened (`eConsole`). The id is NULL when no device is left for that role and is valid only during the call.
  - `OnDeviceStateChanged`'s state is one value (`ACTIVE`, `DISABLED`, `NOTPRESENT`, `UNPLUGGED`). A chosen device coming back is `ACTIVE` with its id. Losing a device needs no notification: the stream's next call fails with `AUDCLNT_E_DEVICE_INVALIDATED`.
  - windows 0.61: `#[implement(IMMNotificationClient)]` on a struct, `impl IMMNotificationClient_Impl for Name_Impl`, string arguments arrive as `&PCWSTR`, `PROPERTYKEY` is in `Win32::Foundation`; `HSTRING` derefs to `[u16]` for comparing ids.
  - An `IAudioClient` from `IMMDevice::Activate` stays on its device and doesn't follow a new default. Reopen it.

## Raw Input

- `RIDEV_INPUTSINK` requires a non-null `hwndTarget`. A message-only window (`HWND_MESSAGE` parent) works.
- Build key identity from `MakeCode` plus the `RI_KEY_E0`/`E1` flags, not just `VKey`, to tell right Ctrl/Alt and Numpad Enter apart. Track modifier state per side.
- Auto-repeat arrives as repeated key-downs. An action fires on the first down only.
- **UIPI:** input to an elevated (admin) foreground window doesn't reach a non-elevated Backsight. Detect it (foreground process elevated, Backsight not) and tell the user.
- Reset modifier state on `WM_INPUT_DEVICE_CHANGE` and when the session locks, to avoid a "stuck Alt" after Alt-Tab or Win+L.
- `WM_INPUT` and `WM_INPUT_DEVICE_CHANGE` are posted, but `WM_WTSSESSION_CHANGE` is **sent** straight to the window procedure; our wndproc reposts it to the loop that owns the matcher *(verify: lock the PC with Alt held)*.
- `RAWKEYBOARD.VKey == 0xFF` marks fake keys inside escape sequences (the extra Shift around PrintScreen or arrows with NumLock on); skip them. Pause arrives with `RI_KEY_E1` and make code `0x1D` *(verify on a real Pause key)*.
- Keys injected with `SendInput` (scan codes, `KEYEVENTF_EXTENDEDKEY` for E0) reach a `RIDEV_INPUTSINK` listener; `tests/raw_input.rs` relies on that.
- Lost key-ups: `GetAsyncKeyState(vk) < 0` means the key is down now. It takes the **virtual** key, which depends on layout (scan code `0x10` is `VK_A` on AZERTY, Numpad 7 is `VK_HOME` with NumLock off), so use the `RAWKEYBOARD.VKey` the key arrived with, not one derived from its name. Mouse buttons: `VK_MBUTTON`, `VK_XBUTTON1`, `VK_XBUTTON2`. It returns 0 while another desktop (UAC, Ctrl+Alt+Del) is active, which reads as "released": fine for ending push-to-talk. Covered by `tests/raw_input.rs` for injected keys held past the 250 ms poll.
- `SetTimer(Some(hwnd), id, ms, None)` posts `WM_TIMER` (`wParam` = id) to the window's thread queue, so `GetMessageW` sees it; the same id only resets it. `KillTimer` stops it.
- A `WM_QUIT` from `PostThreadMessageW` is posted, and `GetMessage` returns it **before** pending input. Don't assume all input sent before a stop was handled.

## Reading media back (FFmpeg 8.1, `backsight-encode/src/media.rs`)

- `AVStream.avg_frame_rate` is frames ÷ duration (a 2 s clip at 30 fps reads 30.5). Use `av_guess_frame_rate` (rsmpeg `AVStream::guess_framerate`), which prefers `r_frame_rate`.
- `AVFormatContext.duration` is in `AV_TIME_BASE` (µs) and covers all streams; MPEG-TS streams start around 1.4 s, so seek to `stream.start_time + offset`.
- `av_seek_frame(..., AVSEEK_FLAG_BACKWARD)` lands on the keyframe at or before the target. Call `avcodec_flush_buffers` after every seek, then decode and drop frames before the target. Place frames with `best_effort_timestamp`, not `pts`.
- Decoders default to one thread; pass `threads=auto`. Set `pkt_timebase` from the stream (`apply_codecpar` doesn't).
- At end of file, `send_packet(None)` once, then `receive_frame` until `AVERROR_EOF`.
- The `mjpeg` encoder takes `yuvj420p` (full range). For fixed quality set `flags=+qscale` and the frame's `quality` (`qscale × FF_QP2LAMBDA`), as `ffmpeg -q:v` does.
- swscale reads the source size from its context, not the frame: rebuild it when a frame arrives at another size, or it reads past the buffer.

## Tauri

- Closing the last window sends `RunEvent::ExitRequested { code: None }` in the same event-loop turn as its `Destroyed` (which comes first). Call `prevent_exit()` to stay in the tray; "Quit" uses `app.exit(0)` (an explicit code). To replace the window, prevent that exit and build the new one from a closure posted after `Destroyed`; rebuild with `WebviewWindowBuilder::from_config` using the `tauri.conf.json` window entry.
- `RunEvent::Exit` runs on the main thread, then the process calls `process::exit`, so anything still running after the handler is cut off (Tauri 2.11).
- **Logoff/shutdown:** tao runs `Exit` inside `WM_ENDSESSION`. While a clip is being saved or a stopped recording is being finished, `backsight-engine/src/shutdown.rs` holds shutdown off (see "Shutdown and sign-out"). A running recording does not hold it off: when Windows goes ahead, the `Exit` handler stops and finishes it within Windows' time limit, and if cut off, the crash-safe file is recovered at the next start. A conversion to MP4 and recovery at start resume at the next start.
- The CSP needs `connect-src ipc: http://ipc.localhost`, or `default-src 'self'` blocks IPC. Tauri then falls back to `postMessage` with only a console warning: small commands work, binary responses (the picker's frozen frame) fail.
- Start `Hotkeys` after `Builder::build()` (e.g. from `RunEvent::Ready`): tao registers Raw Input in `EventLoop::new` and Tauri registers it again in `build()` (`set_device_event_filter`), both before `setup`, and the last registration per process wins. Never call `set_device_event_filter` yourself.
- Sync commands run on the main thread, so they must never wait on a lock the session holds for seconds (`get_status` uses `try_lock`). Start the session in an `async` command inside `spawn_blocking`. Never drop `Hotkeys` while holding a lock its callback takes: drop joins the hotkey thread.
- `#[tauri::command(async)]` on a plain `fn` (tauri-macros 2.7) runs it on the async runtime, and unlike an `async fn` may take `State<'_, T>` without returning `Result`. A call that can get stuck there still holds a runtime worker, so pollers like `get_status` skip while their previous call is running. Wrap blocking work (FFmpeg, folder scans) in `tauri::async_runtime::spawn_blocking`.
- The main thread runs every window and all WebView2 events (IPC included), so a blocked main thread is what makes Windows say "Not responding"; engine threads carry on. `uiwatch.rs` notices with `AppHandle::run_on_main_thread` (a no-op every 2 s; `Err` once the event loop has ended).
- Neither wry 0.57 nor Tauri 2.12 handles WebView2's `ProcessFailed`. Register it through `Webview::with_webview` → `PlatformWebview::controller().CoreWebView2()?.add_ProcessFailed(&webview2_com::ProcessFailedEventHandler::create(..), &mut token)` (webview2-com 0.39, the version wry uses). Kinds: 0 browser process exited (WebView closed: make a new one), 1 render process exited and 2 unresponsive (reload or recreate), 3-9 frame, utility, sandbox, GPU and plugin processes (WebView2 restarts them). It fires on the main thread: change the window afterwards (`run_on_main_thread`), not inside it.
- The asset protocol (`convertFileSrc`, `http://asset.localhost/...` on Windows) needs both the `protocol-asset` cargo feature and `app.security.assetProtocol.enable` (tauri-build fails if they disagree), plus `asset: http://asset.localhost` in the CSP's `img-src`/`media-src`. Grant folders at runtime with `app.asset_protocol_scope().allow_directory(dir, true)`; a folder not yet created should match once it exists *(verify)*. The scope can't un-allow; `forbid_*` is permanent and beats any allow.
- Notifications use `tauri-plugin-notification` from Rust (`app.notification().builder()...show()`); no capability entry needed. An unpackaged dev build may show them under another app name.
- Long checkout paths break MSVC linking (`LNK1104`); see [DEVELOPMENT.md](../DEVELOPMENT.md).
- Updater (`tauri-plugin-updater` 2.14, `update.rs`): `Update::install` verifies the signature, runs the builder's `on_before_exit`, starts the NSIS setup with `ShellExecuteW` (`/P /UPDATE`, plus `/R /ARGS <current args>` because `restart_after_install` defaults to true) and calls `process::exit(0)` at once, skipping `RunEvent::Exit`. Setting `on_before_exit` replaces the default hook, which calls `cleanup_before_exit`. Timeouts default to none. `generate_context!` then needs `serde_json` as a direct dependency. Only Rust calls it, so no `updater:` capability. `bundle.createUpdaterArtifacts` makes `tauri build` require `TAURI_SIGNING_PRIVATE_KEY`.

## Shutdown and sign-out (`backsight-engine/src/shutdown.rs`)

Checked against Microsoft Learn: `ShutdownBlockReasonCreate`, "Shutdown Changes for Windows Vista" and the archived "Application Shutdown Changes in Windows Vista".

- `ShutdownBlockReasonCreate(hwnd, reason)` / `ShutdownBlockReasonDestroy(hwnd)` (user32, `windows` feature `Win32_System_Shutdown`, both `Result<()>`) work only from the thread that created `hwnd`; otherwise `ERROR_ACCESS_DENIED`. So Backsight uses its own hidden window on its own thread, not a Tauri window (disposable; tao owns that loop). It must be top-level: message-only windows get no `WM_QUERYENDSESSION`.
- The reason alone does not block: the window must also answer `WM_QUERYENDSESSION` with FALSE (or answer late). An app answering TRUE is closed whatever reason it registered.
- An app with no visible top-level window (Backsight in the tray) that vetoes without a reason is killed after 5 s. With a reason it's treated like an app with a visible window: Windows shows its full-screen "apps are preventing shutdown" screen with the reason, and the user picks continue or cancel.
- Register the reason before shutdown starts (when the save begins), not inside `WM_QUERYENDSESSION`: only then is Backsight listed when another app blocked first. Keep it short.
- "Shut down anyway" is a critical shutdown: `WM_QUERYENDSESSION` has `ENDSESSION_CRITICAL`, FALSE no longer blocks, and `WM_ENDSESSION` follows. An app with a reason gets 30 s to answer `WM_ENDSESSION` (5 without); once it answers, the process can end at any time. Backsight's window waits there (up to 25 s) for saves to finish.
- *(verify by hand)* Whether Windows carries on by itself once the reason is removed while its screen is showing, or the user must click again.

## Publishing a finished file without replacing one (`backsight-encode/src/fsutil.rs`)

- `std::fs::rename` on Windows replaces an existing destination (`MOVEFILE_REPLACE_EXISTING`), so "check `exists()`, then rename" races: a file created in between is destroyed.
- `MoveFileExW` with no flags fails with `ERROR_ALREADY_EXISTS` (183) if the destination exists, in one step. It needs no hard links (works on FAT, exFAT, SMB, unlike `CreateHardLinkW`) and refuses to copy across volumes without `MOVEFILE_COPY_ALLOWED`.
- The `windows` crate returns an HRESULT; `code().0 & 0xffff` gives the Win32 code, which `io::Error::from_raw_os_error` maps to `ErrorKind::AlreadyExists`.
- Use `fsutil::publish(part, wanted)` for finished recordings and clips: on a taken name it tries `name (2).ext`, `name (3).ext`... and returns the name used. Pre-picking a free name is only a hint.

## Colour and quality measurement (FFmpeg 8.1, `colour.rs` and `quality.rs`)

- swscale's default YCbCr coefficients are BT.601 (`SWS_CS_DEFAULT` = `SWS_CS_ITU601`). Any RGB → YUV step in a test graph must say `scale=out_color_matrix=bt709:out_range=tv`, or the reference has the very matrix bug the test looks for.
- `libvmaf` takes the **distorted** video first and the reference second ([FFmpeg filters](https://ffmpeg.org/ffmpeg-filters.html#libvmaf)); PSNR and SSIM don't care. The gyan.dev 8.1 full build has `libvmaf` with the built-in `vmaf_v0.6.1` model; check `ffmpeg -filters` before assuming another build does.
- Comparing a decoded file with a regenerated `concat` graph paired frames off by one after the first part (even lossless read ~28 dB). Renumber both sides by frame (`settb=1/60,setpts=N`) and check the file's frame count.
- The `gradients` source picks random colours and line points unless `c0`/`c1` and `x0`…`y1` are set (inside the frame); `noise` repeats with `all_seed`. Then the graph is deterministic.
- NVENC and x264 write `color_range=tv`, `bt709` matrix, primaries and transfer into the H.264/HEVC stream, and FFmpeg decodes to plain `yuv420p` without converting, so decoded planes compare directly against expected code values. The D3D11 video processor's BT.709 limited output decoded within ΔE 0.4 of the source on 100% bars and grey steps (scaled 1440p → 1080p).

## Crash reports (`backsight-engine/src/crash.rs`)

- A `std::panic::set_hook` hook runs on the panicking thread before `panic = "abort"` ends the process, so it can write the report; call the previous hook afterwards to keep stderr output. A fast-fail abort (`__fastfail`) skips `SetUnhandledExceptionFilter`, which is why panics are caught by the hook.
- `SetUnhandledExceptionFilter` (`windows` features `Win32_System_Kernel` and `Win32_System_Diagnostics_Debug`, for `EXCEPTION_POINTERS`) sees only this process, once, on the faulting thread, for an unhandled structured exception (access violation etc.). The filter calls the one it replaced (the call returns it) and returns its result, or `EXCEPTION_CONTINUE_SEARCH` (0) when none, leaving Windows Error Reporting as before. No injection or hooks into other processes. *(verify)* not triggered with a real access violation in CI; the filter allocates and may fail if the heap itself is corrupt.
- Rust's stack overflow handler is a vectored handler that aborts; the filter then runs on an exhausted stack and may fail to write.
- A path shows up in text as `C:\Users\Avery`, `C:/Users/Avery`, `C:\\Users\\Avery` (Rust `{:?}`), `file:///C:/Users/Avery%20X` and 8.3 form (`GetShortPathNameW`, existing paths only). `COMPUTERNAME` is cut to 15 characters; `GetComputerNameExW` (`ComputerNameDnsHostname` / `ComputerNameDnsFullyQualified`) gives the full name. A profile folder can be named differently from `USERNAME`.
- Reports are scrubbed before they touch disk (profile path, user name, PC name, e-mail, IPv4, clip file names). Anything new in a report must pass through `crash::scrub`.
- Benching two checkouts in one target dir: `cargo clean --release -p <workspace crates>` between them, or cargo may reuse the other's artifacts; `CRITERION_HOME` sets where baselines go.

## Another thread's stack (`backsight-engine/src/stack.rs`)

- Own process only, no debugger: `OpenThread(THREAD_SUSPEND_RESUME | THREAD_GET_CONTEXT)`, `SuspendThread` (`u32::MAX` on failure; the pause is asynchronous and `GetThreadContext` waits for it), `GetThreadContext` with `CONTEXT_CONTROL_AMD64 | CONTEXT_INTEGER_AMD64` (the `windows` `CONTEXT` is already 16-byte aligned), then `ResumeThread`.
- x64 unwinding without dbghelp: per frame `RtlLookupFunctionEntry(rip, &mut image_base, None)`; null means a leaf (return address at `[rsp]`, then `rsp += 8`), else `RtlVirtualUnwind(UNW_FLAG_NHANDLER, ...)` updates the context to the caller. Stop at `rip == 0`, when `rsp` leaves the thread's stack (`GetCurrentThreadStackLimits`, taken on that thread beforehand), or when `rsp` doesn't grow. Both are in kernel32 (`Win32_System_Diagnostics_Debug`).
- While the thread is paused, don't allocate or take locks it might hold (the heap lock): allocate before `SuspendThread`, look modules up after `ResumeThread` (`GetModuleHandleExW(FROM_ADDRESS | UNCHANGED_REFCOUNT)`, `GetModuleFileNameW`). `RtlLookupFunctionEntry` may still take a loader lock the paused thread holds (rare).
- Release builds need `debug = "line-tables-only"` and `strip = false` for a PDB: on MSVC `strip` passes `/DEBUG:NONE`. With `/DEBUG` rustc embeds only the PDB's file name (`/PDBALTPATH:%_PDB%`), not its folder.
- `HKEY` is in `Win32::System::Registry`, not `Foundation`. `DisplayVersion` and `ProductName` under `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion` give "Windows 11 Home 25H2"; Windows 11 still reports `ProductName` "Windows 10", so include the build number.

## HDR video

- [Microsoft's WGC guidance](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture) uses an RGBA16F pool throughout HDR capture; keep that format when recreating the pool. [Windows Advanced Color](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/high-dynamic-range) defines linear scRGB with BT.709 primaries, 1.0 = 80 nits. Check the chosen monitor's active DXGI colour space across adapters (display and encoder can be on different adapters).
- [FFmpeg 8.1 NVENC](https://ffmpeg.org/doxygen/8.1/nvenc_8c_source.html) accepts system-memory P010 and writes the HEVC colour description from the codec context. Backsight sets Main 10, limited range, BT.2020 non-constant luminance and ST 2084; the muxer gets the same codec parameters for replay and recording. Display EDID describes the playback display, so it's unsuitable as mastering or content-light metadata for captured material; Backsight writes none.
- HDR is chosen at session start; restart capture after changing Windows HDR mode. It needs NVIDIA HEVC and MP4 or MKV; turning it on in the Video page switches to those (`app/src/lib/hdr.ts`). The engine never refuses to start over HDR: unsuitable settings or an encoder that won't open in HDR record SDR with a Home notice (`target::hdr_settings`, `HdrFallback`). A monitor whose DXGI colour space isn't `G2084_NONE_P2020` records SDR with a notice (`target::start_notice`); when DXGI can't say (no factory or output) it also records SDR, logs why, and the notice says it couldn't check. Library thumbnails and previews don't tone-map PQ.
- **The D3D11 video processor can't make HDR video** (a recent NVIDIA driver): `CheckVideoProcessorFormat` gives FP16 as input only, and `ID3D11VideoProcessorEnumerator1::CheckVideoProcessorFormatConversion` returns FALSE for FP16 `RGB_FULL_G10_NONE_P709` → P010 `YCBCR_STUDIO_G2084_LEFT_P2020`, FP16 → R10G10B10A2 `RGB_FULL_G2084_NONE_P2020`, and R10G10B10A2 PQ → P010 PQ (BGRA → P010 G22 709 is TRUE). So `capture/hdr.rs` converts with a compute shader (cs_5_0, compiled once per process with `D3DCompile` from the system `d3dcompiler_47.dll`, feature `Win32_Graphics_Direct3D_Fxc`, so a resize doesn't recompile in the capture callback) into a P010 texture, then copies it into FFmpeg's D3D11 P010 frame (zero copy to NVENC, `sw_format = P010`). Those FFmpeg P010 textures get no bind flags (they are only copied into; render-target support for P010 isn't guaranteed; NV12 keeps `D3D11_BIND_RENDER_TARGET` for the video processor). The shader holds 60 FPS at 1440p, even in a debug build; a CPU version (readback, per-pixel `powf`) took ~315 ms per frame.
- **Chroma siting:** HEVC VUI without `chroma_loc_info_present_flag` means location type 0, left-sited (co-sited with even columns, between rows), and FFmpeg 8.x `nvenc.c` never sets one. The shader therefore filters chroma [1/4 1/2 1/4] across columns x−1, x, x+1 and averages the two rows. `chroma_sample_location=left` is still set on the codec context: MKV records it (`ChromaSitingHorz`), MP4 doesn't.
- **Writing P010 from a shader:** P010 reports `TYPED_UNORDERED_ACCESS_VIEW` and `D3D11_FORMAT_SUPPORT2_UAV_TYPED_STORE` on NVIDIA and WARP. Make one UAV per plane with `ID3D11Device3::CreateUnorderedAccessView1` (`R16_UNORM`, `PlaneSlice` 0 for Y; `R16G16_UNORM`, `PlaneSlice` 1 for interleaved CbCr). P010 keeps the 10-bit code in the top bits, so store `code * 64 / 65535`. Matches the CPU formula within one code value on both (`capture::hdr` tests).
- **What the capture holds:** WGC's FP16 frames are absolute scRGB (1.0 = 80 nits), so SDR content sits at Windows' SDR white level: `DisplayConfigGetDeviceInfo` with `DISPLAYCONFIG_DEVICE_INFO_GET_SDR_WHITE_LEVEL` (type 11) gives `SDRWhiteLevel` in thousandths of 80 nits (1000 = 80 nits; SDR monitors report 1000). A hand tone-mapped HDR clip matched a JPEG XR screenshot of the same desktop (peak 80 nits at an 80-nit SDR white). The level can change at any time (280 nits to another value within an hour), so read it when needed rather than caching.
- **Game window mode:** Microsoft documents nothing about FP16 window capture. OBS's `libobs-winrt/winrt-capture.cpp` treats windows and monitors alike: an `R16G16B16A16_FLOAT` pool only when `MonitorFromWindow` gives an HDR monitor, else BGRA8, and FP16 window frames as scRGB scaled by the SDR white level. What FP16 frames hold for a window on an SDR monitor is unknown. Backsight does the same: the encoder opens before the game's window is known, so the start checks the monitor in front (`wgc::foreground_monitor`) and the pool keeps the session's format. The follower compares the captured window's `MonitorFromWindow` every poll and rechecks HDR only on change. When the game sits on (or is dragged to) the other kind of monitor, `monitor_moved` asks the app for one restart (`target::window_hdr_restart`; never for settings or an encoder that can't do HDR or a monitor Windows can't say about; never during a recording, Home says it waits); dragging back or closing the game first cancels it. Windows HDR switched on later isn't noticed until the next start, so Home asks for Instant Replay off and on. The restart gets the captured program (`ReplaySession::captured_window`): if that window is still open it checks its monitor and captures it straight away, so another window in front can't take its place. Until the restart the window keeps its pool. A new window capture's first frame skips the size debounce (a still window sends one frame and no more; otherwise the video stayed black after a restart). Captures are numbered and frames from an older capture are ignored, so a replaced window can't put its picture back. The `hdr_video` `game_window` test checks that the window sent frames, Home's line, the clip's pixel format and transfer tags, and that the last frame isn't black (keep a bright window such as Notepad in front). Checked on an HDR monitor: HDR and SDR monitors, drags in both directions with a restart, and a restart with Character Map in front. *Still to measure: FP16 window values against monitor capture of the same picture.*
- **SDR video on an HDR monitor is fine:** WGC's BGRA8 pool maps the SDR white level to 255, so desktop and SDR games aren't washed out or dark (clip luma 16-236). Highlights above SDR white clip, as expected.

### HDR test pattern (`tests/support/pattern_window.rs`)

- **The HDR10 swap chain:** `R10G10B10A2_UNORM` plus `IDXGISwapChain3::SetColorSpace1(RGB_FULL_G2084_NONE_P2020)` is Microsoft's ["Option 2"](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/high-dynamic-range) HDR10 path, for swap chains that don't need alpha blending. It must be flip model (`FLIP_DISCARD` or `FLIP_SEQUENTIAL`). The default colour space for R10G10B10A2 is sRGB, so the call is required; the test makes it before the first Present (the docs don't say whether that's required).
- **Don't gate on `CheckColorSpaceSupport`.** In windows 0.62 it returns `Result<u32>`; test against `DXGI_SWAP_CHAIN_COLOR_SPACE_SUPPORT_FLAG_PRESENT.0 as u32` (1). Its [page](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/nf-dxgi1_4-idxgiswapchain3-checkcolorspacesupport) says unreported spaces may still work, so the `SetColorSpace1` result counts. Whether Windows HDR is on comes from `IDXGIOutput6::GetDesc1().ColorSpace`, as in the engine.
- **Skip `SetHDRMetaData`:** it "does not change how pixel values are interpreted" ([page](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_5/nf-dxgi1_5-idxgiswapchain4-sethdrmetadata)) and is no longer recommended.
- The device is made with `D3D11CreateDevice(&adapter, D3D_DRIVER_TYPE_UNKNOWN, …)` on the adapter that owns the monitor's output (an explicit adapter needs `UNKNOWN`).
- **What DWM does with PQ:** with Windows HDR on, DWM converts each surface to its FP16 scRGB composition (matrix plus 1D LUT); the PQ wire format and any MHC calibration come later, at scanout. WGC captures the composition, so it should see neither, but no page says what WGC taps. Not documented: DWM clipping light above the panel's peak (1000 nits should arrive as ~12.5 on a 400-nit panel); whether colours outside BT.709 (negative scRGB) survive (the calibrated check measures with BT.2020 primaries). On panels with a brightness slider (laptops) Windows scales HDR luminance invisibly to apps, and whether before capture is undocumented, so run absolute-nit checks on an external HDR monitor.
- **Not documented, measure instead:** whether WGC still captures a borderless full-screen flip-model window that gets independent flip (commonly reported to work, since DWM still composes for capture); the FP16 values of window capture against monitor capture on HDR and SDR monitors (see "Game window mode"); whether Auto Color Management on an SDR monitor changes BGRA8 capture values.

## What Instant Replay costs (`scripts/replay-cost-matrix.ps1`)

Measured on an NVIDIA PC capturing an external 1440p HDR monitor into 1080p, with a debug build of the engine's cost test. "Game" is the script's stand-in: a full-screen window drawing a heavy shader flat out, so the card sits at full clock (~1.95 GHz, 80 W) and percentages are comparable; its pictures per second are what a game would lose. Re-measure with the script on another PC.

- **Read percentages with the clock next to them.** Task Manager's per-process GPU figure is the busiest engine as a share of time at the *current* clock: the same still-screen work read 11% of the encoder at 210 MHz and 8 W (0.6 W over idle). Windows' counters also miss work (off-screen drawing read 0.7% "3D" while nvidia-smi said 95% busy): trust pictures per second and watts over small percentages.
- **Bitrate costs nothing on the card** (HEVC 1080p60 P1 at 5, 20, 50 Mbps: encoder 12.2 / 12.4 / 12.4%). Rate control (VBR, CBR, constant quality) and tuning (`hq`, `ll`, `ull`) change nothing either.
- **Frame rate and size cost in proportion:** 30 FPS is half of 60 (4.7% vs 8.9%); 720p 4.3%, 1080p 8.9%, 1440p 13.9% (HEVC P1, no B-frames). P4 costs 15.4% vs P1's 8.9%.
- **B-frames are the expensive default.** Two B-frames: HEVC encoder 12.4% vs 8.9% without, 3D 3.3% vs 0.7%; H.264's encoder time is unchanged but its 3D work also goes 3.0 → 0.7%. So NVENC's catalog default is 0 B-frames. Look-ahead adds 1 point of encoder and 2.1 of 3D, both AQ modes 2.5 of 3D, quarter-resolution multipass 2.2 of encoder and 2.3 of 3D: all off by default.
- **What a game loses:** ~150 pictures/s with replay off, ~147 on (2-3% less), whatever the bitrate, frame rate, size or codec. About 2% is the price of capturing at all (Windows' capture copies, power shared with the encoder), not of the settings.
- **HDR costs little more than SDR:** 1440p HDR into 1080p60 without B-frames, encoder 8.5%, 3D 1.1% (SDR 0.7%).
- **A still screen:** WGC sends nothing, so every slot was a repeat and the encoder ran 60 times a second for nothing (33-37% of the encoder, 10% of 3D). Now (`session.rs`, `still_slot`) about 15 a second: 11.2% and 5.4% at 210 MHz, 8.2 W vs 7.6 W idle.
- The baseline drifts for minutes after a load starts (150 → 111 pictures/s in one run, compositor share 1% → 14%): warm up for a minute, put an `off` row before and after what you compare, and don't compare rows far apart.

### Leaving frames out safely (NVENC, FFmpeg 8.1 `nvenc.c`)

- FFmpeg holds NVENC's output back on purpose: `delay` (`async_depth`, default "as much as allowed") is clamped in `nvenc_recalc_surfaces` to `nb_surfaces - 1`, with `nb_surfaces = max(4, 4 × (B-frames + 1))`, more with look-ahead. `output_ready` releases a packet only once that many frames are queued: **3 frames without B-frames, 11 with two**. At 60 fps nobody notices; at a few frames a second the last pictures arrive seconds late, which broke A/V sync when repeats were first skipped.
- `delay=0` would release every packet at once, but `receive_packet` then waits for the card every frame (`nvEncLockBitstream` with `doNotWait = 0`) on the thread that paces video, and it silently turns look-ahead off (`lkd_bound < 0`). Not used.
- What works: when pictures stop, `avcodec_send_frame(NULL)`, receive until EOF, then `avcodec_flush_buffers` (`VideoSession::rest`). Only NVENC does this (`can_rest`); other encoders encode every slot. `AV_CODEC_CAP_ENCODER_FLUSH` isn't enough to go by: libx264 has it, but after draining it refuses the next frame ("lookahead thread is already stopped"). AMF is untested. With NVENC the stream goes on without a new keyframe and decodes cleanly, with and without B-frames (`tests/replay_session.rs`).
- **Decode times across a flush with B-frames** (`nvenc_set_timestamp`, `ff_nvenc_encode_flush`): `delay` = `frameIntervalP - 1`. The flush empties the queue of input times and resets `output_frame_num` and `initial_delay_time`. The first `delay` packets after it get `queue[0] - D * (delay - k) / delay`, where `queue[0]` is the run's first input time and `D` = `queue[delay] - queue[0]` if that many inputs are queued, else `delay` ticks; every later packet gets the next queued input time. Before the flush the last decode time is the input time `delay` frames before the last one. With contiguous frames decode times already rise, but a slot skipped early in a run makes `D` larger and the first decode time can reach back to or before the last. Fix (`rising_dts` in `backsight-encode/src/session.rs`): bump a decode time that doesn't rise to `last + 1` **in encoder ticks**, before converting to microseconds. It always fits: at least `delay` free ticks lie between the last decode time and the run's first picture, and later decode times are past them. Bumping in rounded microseconds fails: `last + 16 667 µs` can land 1 µs past the next tick, then every packet is bumped 1 µs more until decode passes display time and MP4 refuses it. NVENC rests with any B-frame count; unit tests in `session.rs` replay this for 1-4 B-frames.
- `zerolatency` only sets `rcParams.zeroReorderDelay`; it doesn't change FFmpeg's hold-back.
- The encoder check still opens NVENC with two B-frames (`probe.rs`), so a card that can't do them is known before someone turns them on.
- **WGC dirty regions on an HDR monitor** (recent Windows 11 builds): any change, even one small animating window, is reported as one rectangle covering the whole screen, and no frame came with an empty list. On an SDR monitor a still screen simply sends no frames. Dirty regions therefore don't help still detection; the replay rests when WGC sends nothing.

## Captions (whisper.cpp through whisper-rs 0.16, ADR 0016)

- **The `cmake` crate builds C/C++ without `/O2` on MSVC.** It passes cc's flags, built with `opt_level(0)`, as `CMAKE_<LANG>_FLAGS_<CONFIG>`, which replaces CMake's defaults: the Visual Studio project gets an empty `<Optimization>`, so `/Od`. Whisper base then took over 3 minutes for 60 s of speech instead of about 25 s. The crate skips that variable when it is already defined, and `whisper-rs-sys` defines every `CMAKE_*`, `GGML_*` and `WHISPER_*` environment variable, so `.cargo/config.toml` sets `CMAKE_C_FLAGS_RELEASE`/`CMAKE_CXX_FLAGS_RELEASE` in full. The configuration is `Release` only when the package is optimized without debug info (`OPT_LEVEL`, `DEBUG`), hence the `whisper-rs-sys` profile overrides in the workspace `Cargo.toml`. Check: the `ggml-cpu.vcxproj` under the build's `out/build/ggml/src` shows `<Optimization>MaxSpeed</Optimization>` for Release. `build.rs` reruns only when its inputs change: `cargo clean -p whisper-rs-sys` after changing these.
- **`GGML_NATIVE=OFF`** turns on AVX, AVX2, BMI2, FMA and F16C (`INS_ENB`) and nothing newer (no AVX-512), so the build needs a CPU with those. `cpu_supported()` checks them with `is_x86_feature_detected!` before loading anything. Runtime CPU dispatch (`GGML_CPU_ALL_VARIANTS`) needs `GGML_BACKEND_DL` and DLLs per variant; not used.
- **whisper-rs's `WhisperState::full` calls `whisper_full_with_state`, which skips the built-in VAD** (only `whisper_full` runs it): `enable_vad(true)` silently does nothing. Backsight runs `WhisperVadContext::segments_from_samples` itself (times in centiseconds, as `f32`), joins the stretches with 0.1 s of silence and maps times back (`cues.rs`). Whisper's token end times often run 0.1–0.3 s into the next stretch, so an end is never mapped past the stretch its start is in. `WhisperVadContext::new` and `set_vad_model_path` leak their path `CString` (whisper-rs 0.16); a few bytes per process.
- **Silero VAD v6.2.0** (`ggml-silero-v6.2.0.bin`) loads in whisper.cpp 1.8.3 (the version in whisper-rs-sys 0.15).
- **Background mode for every thread.** `THREAD_MODE_BACKGROUND_BEGIN` covers only the calling thread, and ggml starts its worker threads at normal priority (no OpenMP: one threadpool per graph compute, `GGML_SCHED_PRIO_NORMAL`, not settable through whisper.cpp). So captions run in their own process, which sets `PROCESS_MODE_BACKGROUND_BEGIN` on itself ([SetPriorityClass](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setpriorityclass); `windows` 0.62: `SetPriorityClass(HANDLE, PROCESS_CREATION_FLAGS) -> Result<()>`). Background disk priority made the first model read take 72 s once on a busy drive (0.3 s normally), so the process reads the models first and enters background mode after.
- **Measured** on a test laptop (Core i5-12500H, 12 cores/16 threads; other programs keeping the CPU at about 75%), base q5_1, greedy, 2 threads, speech joined by VAD:

  | Audio | Background mode | Time |
  | --- | --- | --- |
  | 60 s, about 33 s of talking | caller thread only (one ggml thread normal) | 22–33 s |
  | 58 s, about 7 s of talking | caller thread only | 11–12 s |
  | 60 s, 33 s of talking, no VAD | normal priority, 4 threads | 16 s |
  | 71 s, about 40 s of talking (the app's process path) | whole process | 48 s |
  | 58 s, about 7 s of talking (the app's process path) | whole process | 28 s |

  Without VAD the silent 58 s took 16 s and Whisper placed every line at the wrong time (speech at 8 s shown from 0 s). Model load 0.2–0.3 s warm. Peak working set 265–315 MB, peak commit about 800 MB, all freed when the process ends. VAD alone: 0.7–1.3 s per minute. Token timestamps and `max_len` cost nothing measurable. Background mode on a busy PC roughly doubles the time; it is what keeps the game's frames. *(verify the game's FPS while a caption job runs.)*
